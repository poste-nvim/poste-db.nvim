## 一、已修复的 bug（8 个提交）

### 1. 被取消的一次运行会作废在途请求的响应（de2a4b5）

`sql_runner.run_sql_request` 在「缺连接」「DML 守卫拒绝」两个取消路径
**之前**就推进了 `exec_seq`、清除指示器、写历史条目、清面板。后果：
①请求 #1 还在跑时用户取消请求 #2，epoch 前移让 `sql_runner/response`
的 stale-seq 守卫把 #1 的响应静默丢弃（查询成功了却什么都没显示）；
②历史侧栏多出一条空条目；③指示器/面板被清给一个从未开始的运行。
所有「运行真正开始」的副作用现在统一放在每条取消路径之后（紧挨
`session.begin`），原注释声称的语义如今才名副其实。

### 2. 错误上下文 `state.last_error.sql` 无界增长（9a24c5d）

多语句运行里失败分支给 `get_stmt_sql` 的 max_end 传的是
`visual_sel_end or #buf_lines`，成功分支却是 `... or stmt_end or ...`——
非可视多语句运行的错误上下文（AI「问这个错误」动作发送的内容）会拖到
缓冲区末尾。补齐 `stmt_end` 回退。

### 3. `vim.NIL` 进 `file_exec` 的三处崩溃/污染（8efeefd）

浏览器树里 `meta.database` 为 JSON null 的节点执行 Execute SQL File 时，
`vim.NIL` 为真值且 `~= ""`：落在 jobstart 的 argv 上（userdata 软失败）、
在进度对话框 `.. S.db` 处直接抛错、并原样写进 SQL 日志。回归测试先抓到
argv 一处，跑起来后又抓到对话框第二处——根修是 `run()` 入口用
`util.named` 归一化 `conn`/`database`（与 `exec_run.build_cmd` 同款防护）。
同提交顺带：事件缺 `total` 时保留旧值（`string.format("%d", nil)` 会在
job 回调里裸抛），删除只写不读的 `S.current_sql`/`S.total_rows`。

### 4. `config.merge` 用索引合并污染列表选项（f5a0bf5）

`vim.tbl_deep_extend("force")` 对数组按索引合并：
`setup({ sql_formatters = { "pg_format" } })` 会保留三个被排除的默认
格式化器当后备、新条目重复排在第 4 位——更短的列表永远无法收缩默认值
（`source_format` 正是从这个列表里挑格式化器的）。列表对列表改为整体
替换；空表仍走合并（对列表是无操作，对 keymaps 是「不覆盖」）。

### 5. connections 的四个问题（cb060c4）

- **picker 行丢失 `tunnel` 字段**：`format_connection` 的 🔒 标记与
  `run_test` 的隧道测试路由读 `conn.tunnel`，但 `list_connections` 的行
  构造从来不带它——两者对 picker 来源的连接全部失效。
- **`apply_env` 不展开嵌套表**：`tunnel = { to = "{{BASTION}}" }` 把字面
  `{{BASTION}}` 送进 `tunnel.ensure`，报错形态像是隧道问题而非配置问题。
- **`env.json` 无缓存**：`get_env_vars` 在每次状态栏求值和光标移动时调用，
  dotenv 有 mtime 缓存而 env.json 每次都 `find_file_upwards` + `readfile`
  + JSON 解码。补上同款缓存（键含 `current_env`）。
- **sqlite `path = ""`**：`conn.path or ":memory:"` 对空串不生效，产出
  非法 URL `sqlite:?mode=rwc`。空串视为未设置。

同提交把「当前文件缓冲区目录，否则 cwd」的四处手写副本
（connections/commands/health/completion-data）合并为导出的
`connections.get_search_dir()`，并加 buftype 守卫：伪缓冲区
（`poste://dataset`、`poste://db_browser`、`health://`）的名字非空但不是
文件，旧规则把搜索根解析成 `poste:`、`health:`，状态栏和 `:checkhealth`
可能读到与正在编辑的 SQL 文件不同的 connections.toml。

### 6. db_browser 五项 + 补全/语句两小项（9c58a8e）

- **`db_browser/completion.lua` 把函数当表索引**：`filter_types` 绑定
  `adapter.completion_item_kind`（是个函数）再取 `.TypeParameter`——
  Modify/New Column 表单的键入级类型补全每次请求都抛
  "attempt to index a function value"。改为调用它。
- **粘贴目标方言回退错**：sqlite 连接下的表节点 `meta` 不带 dialect
  （只有连接/库节点带），`resolve_paste_target` 一路落到 yank 条目的
  方言——postgres 表 yank 后贴到 sqlite 连接上能通过方言不一致守卫，
  然后 postgres 风味的 catalog/DDL SQL 打到 sqlite 上。walk-up 找到的
  连接节点现在优先于 yank 条目。
- **恰好 8 项的粘贴计划出现 "and 0 more"**（`i >= 8` 在第 8 项列完
  之后仍然触发）。
- **`run_ddl_and_refresh` 的 on_error 不刷新子树**：`refresh_subtree`
  在任务启动前就清了子节点、置 loading，传输失败（二进制消失等，
  按 exec_run 契约只走 on_error 一次）后节点永远卡在 loading 标记。
- **journal 的 and-or 链**：成功但 stderr 有输出时，
  `parsed_result and nil` 为假落到 `err_text`——success 行携带错误消息。
  改为显式 if。
- **`extract_table_name` 把标识符里的 JOIN 当关键字**：只查了前一个字符，
  `SELECT joined_at, join_date FROM users` 数出两个 JOIN 返回 nil，
  标签退化成 "result n"。前后两个词边界都查。
- **指令补全无词边界**：`-- @connectionX`（手滑）会匹配分支、因取不到
  前缀而列出全部连接名。分支检查补 `%s` 或行尾锚。

### 8. 方言解析三份合并（113dacc）

`diagnostics.lua` 与 `syntax.lua` 各有一份逐字节相同的 `get_dialect`，
`source_format.resolve_dialect` 是第三份**漂移的分叉**：它丢了

## 三、记录未修的项（按证据列出；下一轮或专门会话处理）

性能（P）：

- **P1 每键 3–6 次全缓冲上下文解析**：`completion/handlers.lua` 六处
  `data.conn_key()` 不传 ctx，而 `data.resolve_current_context` 直连
  `context.resolve_full_context`（全缓冲扫描、无缓存）。`ensure_columns/
  ensure_tables/ensure_databases` 内部已各解析一次，修法是让它们的回调把
  已解析的 ctx 带出来、handlers 用 `conn_key(ctx)`。动 house scaffold 的
  回调契约，本轮不仓促改。
- **P2 语义诊断每语句一次全缓冲解析**：`semantic_diagnostics.lua` 在
  语句循环内调 `resolve_full_context`（:626 一带，另有 :571 的默认
  ctx）——S 条语句 × L 行，每 300ms 防抖一轮。header 扫描结果对所有
  语句相同，可提出来复用。
- **P3 三个语法高亮器 TextChanged 无防抖全缓冲扫描**（`autocmds.lua`
  的指令高亮 + 数字前缀 + 已知错误构造）；对比 diagnostics.lua 有
  300ms 防抖。
- **P4 格式化每候选阻塞至 10s**：`source_format` 对每个已安装且报错的
  格式化器 `vim.system` + `:wait(10000)` 串行等待。
- **P5 db_browser 每 CursorMoved `redrawstatus`**（`db_browser/init.lua`
  的 statusline.update）——每次击键重建状态栏字符串。

设计/正确性（D，均已核实机制，影响取决于使用面）：

- **D1 三个响应分类器分叉**：`exec_run.build_response`（多一个
  `is_query_sql` 平决）、`session_conn` 单语句路径（`aff == nil` 即查询）、
  `session_conn` 序聚合器（columns/row_count 也算）。同一事件走不同
  传输可能得到不同信封类型。对齐点在 binary contract（schema.md 说
  SELECT 总是带 columns），先定契约再合并。
- **D2 introspect job 无超时**：`completion/data.lua` 的
  `start_introspect_job` 与 `semantic_diagnostics` 的 run_introspect 都是
  裸 `jobstart`——挂死的二进制会永久压住补全抓取与该 buffer 的语义
  检查。对比：context-detect 路径有 2s 超时。
- **D3 语义诊断 schema 抓取无 epoch 守卫**：DDL 后 `invalidate` 已在途
  的抓取返回后仍会把旧 schema 写回缓存（窗口 = 一次 introspect 往返）。
  completion 缓存已有同款 epoch 方案可抄。
- **D4 DML 关键字遍历无 visited-set**：一个 ERROR 节点含两个 DML
  关键字时互递归（栈溢出被 `M.update` 的 pcall 吞掉 → 诊断静默丢失）。
  加 visited-set 即可，但需要先用探针确认 parser 真会产出该形状。
- **D5 statement 的前向 `;` 扫描跨 `###` 块**：fallback 路径
  （TS 与 binary 都失败时）的 `stmt_end` 可能落进下一个块，合成块携带
  两个标记、执行多跑一条语句。仅在双降级路径可达。
- **D6 diagnostics 的防抖计时器是模块级单例**：B 缓冲区击键会取消 A
  缓冲区已排定的诊断更新，下次事件自愈。对比 `sql_runner` 的
  `_cursor_moved_timers` 已按 buffer 分键。
- **D7 块注释嵌套三种读法**：`lex.block_comment_depth_after` 支持嵌套，
  `blank_regions`/`is_comment_or_string` 不支持（spec 钉了后者的一部分）。
  postgres 嵌套注释下两套扫描可能对同一文本判定不一致。
- **D8 db_browser 多选按节点身份**：刷新子树替换 `children` 后标记消失
  而 winbar 计数与 `p`/`D` 仍作用于旧节点（名字仍正确）。
- **D9 copy_progress 的 results 按 label 键控**：PG 里 trigger 与其表
  同名合法，两个任务读写同一槽位（行状态显示串扰，计数正确）。
- **D10 db_browser 三组 DRY**：五处手写「失效-重取-重绘」绕过
  `util.refresh_subtree`；四处「从 root_nodes 解析方言/连接」绕过
  `util.get_dialect`/`find_table_node`（yank 键映射那份还有「表名恰好
  等于连接名」的隐患）；`copy_progress` 与 `ops_drop` 两套并行的进度/
  摘要对话框。
- **D11 执行链两组 DRY**：journal-wrap 缝隙在 `executor.lua` 与
  `exec_run.lua` 各一份；`UNEXPLAINED_FAILURE` 措辞三处两样（verdict
  依赖无关是刻意的，`sql_log` 可安全 require verdict 对齐）。
- **D12 toml.lua 残余 fail-open 窄边缘**：`k = "a" "b"`、`k = "a\"`、
  `\uXXXX` 转义未实现、`k = 1 2` 会静默存下与 TOML 语义不同的值
  （实测；其余已 fail-closed）。
