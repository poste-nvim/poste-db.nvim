## 一、已修复的 bug（3 个提交）

### 1. 空白新增行产出非法 INSERT（49b3891）

数据集里按 `o` 新增一行、一个单元格都不填就提交，`dml.generate_insert`
会产出 `INSERT INTO "t" () VALUES ();`——除了 MySQL 以外所有引擎都是
语法错误，用户看到的是一句裸的服务端报错。现在按方言产出合法形式：
postgres/sqlite/mssql 用 `DEFAULT VALUES`，MySQL/MariaDB 保留空列表写法
（引擎本身就认），ClickHouse 没有默认值 INSERT 形式、明确拒绝；
`generate_dml` 的 insert 调用点同步处理了新的 nil 返回（原因进
`skipped` 列表，不再产出 `{ sql = nil }` 语句）。

### 2. MySQL 文本列的 ISO 时间戳被静默改写（49b3891）

`dml.quote_val` 的 MySQL 路径把 `2024-01-01T10:00:00Z` 改写成
`'2024-01-01 10:00:00'`，且不区分列类型：VARCHAR 单元格提交后存储值
变了，WHERE 子句同样被改写、语句不再命中它原本指向的行。改写现在只在
列类型含 time/date（或调用方没有类型信息时保持旧行为）才发生。
实测复现：`UPDATE \`t\` SET \`memo\` = '2024-01-01 10:00:00' WHERE
\`memo\` = '2024-01-01 10:00:00'`（列声明为 varchar）。

### 3. 时间戳显示丢失亚秒部分（8618ca1）

`format.format_datetime_local` 只匹配到整秒，`2024-01-01T00:00:00.123456Z`
渲染成本地时间后 `.123456` 消失——timestamp(6) 列的两个值相隔 200ms
会显示成同一秒。亚秒部分现在原样保留在转换结果之后。

### 4. 关闭一个 buffer 会误杀同连接其他数据库的会话（5605d66）

`session_conn.cleanup_buf` 调用 `M.stop(key)`，而 `M.stop` 按 URL
扇出、关闭该连接**所有**数据库的会话：两个 buffer 各连同一服务器的
不同库时，关掉第一个 buffer 会连第二个 buffer 正在用的会话一起杀——
在途请求报 "SQL session exited"、`SET`/临时表状态全部丢失。
现在 `cleanup_buf` 按单个池键逐个关闭（新的 `stop_one`），URL 扇出
只保留给 `:PosteDbSessionStop <url>`。顺带修掉同函数在 `pairs()`
遍历中删除非当前键的问题（Lua 未定义行为；`stop_all` 的注释早就记录
了这条规则，`cleanup_buf` 没有照做）。

## 二、复核后判定「不是问题」的项（留档，避免下一轮重复怀疑）

- **`toml.lua` 字面量字符串里的尾随反斜杠**（`p = 'a\'`）——实测解析
  正确（返回 `a\`），`strip_inline_comment` 的状态机对 literal string
  不处理转义，是有意设计并有注释。
- **`dialect_table_exists_sql` 的 else 分支兜底到 `sqlite_master`**——
  mssql/clickhouse 若走到这里会拿到 sqlite 的探针 SQL，但
  `catalog.enumerate` 在更上游就以 "Unsupported dialect for copy"
  拒绝了这两个方言，路径不可达。若日后把 copy 扩展到 mssql，
  这里需要补 information_schema 探针（见第四节）。
- **`import/format.parse_csv` 里 `local next` 遮蔽全局**——项目
  luacheck 配置（`.luacheckrc`）0 告警，属可接受写法，不动。
- **`db_browser/copy.lua` 冲突名探测失败时 fail-closed**（返回
  "存在"）——有意为之，避免在权限受限的 information_schema 上把已
  占用的名字当成空闲然后覆盖。
- **`log_viewer.get_entry_at_cursor` 只检查 buf 有效性不检查 win**——
  浮层 `bufhidden = "wipe"`，窗口关闭必然带走 buffer，两者生命周期
  一致，不会出现 buf 有效而 win 失效的组合。
- **`dataset.compute_view_indices` 的混合类型排序比较器**——用 6 种
  混合类型（number/string/bool/nil/数字字符串）实测，顺序稳定一致，
  nil 恒排最后，无 "invalid order function" 风险（NaN 在 JSON 传输层
  已变成文本，不会以 double 形态进入比较）。
- **`format.wrap_line` 在 width=0 时**——超宽单词各占一行溢出显示，
  注释里明确记录了这个选择。
- **性能**：`width.display_width` 对纯 ASCII 走字节长度快速路径；
  `format_datetime_local` 每个时间单元格算一次本地时区偏移
  （4 次 os.time/os.date 调用，微秒级），不值得缓存。

## 四、观察项（不确定是否有实际影响，暂不动）

1. **`copy_ddl.dialect_table_exists_sql` 的方言缺口**——如上，当前
   不可达，但它是「copy 支持新方言时第一个会错的地方」。建议扩展
   copy 方言时一并补 mssql（`sys.tables`）与 clickhouse 探针。
2. **`exec_run.run_sql`（同步路径）30 秒超时后**——`vim.system` 的
   timeout 触发时 `result.code` 可能为 nil，失败消息会变成
   "exec-file exit code nil"。仅消息可读性问题，不影响行为。
3. **`export.format_json` 对列为 JSON null（vim.NIL）的键名**——
   `tostring(col.name)` 会产出键名 `"vim.NIL"`。真实二进制不会为
   resultset 列发 null，只有手造响应才会走到；未改。
4. **`exec_run.is_query_sql` 不识别括号开头的语句**（`(SELECT 1)
   UNION ...`）——它只是 Rust 侧 QueryKinds 判定之后的 tie-breaker
   （见该函数上方注释），括号形且驱动同时漏报列/行数才会误判，
   未改。
